# GodotForge 团队协作规则

## 通用规则

1. **godot-forge CLI 优先** — 所有 Godot 项目操作必须通过 godot-forge CLI，禁止手动编辑 .tscn/.tres/.godot 文件
2. **工作目录规范** — 任务产出物放在指定工作目录，Godot 文件放在 game/ 目录内
3. **日志规范** — 每次重要操作后写入活动日志，方便回溯和协作
4. **通知规范** — 关键节点（任务创建、提交、审查、异常）发送通知
5. **文件命名** — 场景/脚本使用 snake_case，有意义的名称，避免 temp、test

## Godot 项目规范

1. **场景路径** — 场景放在 `scenes/` 目录，按功能分子目录 (players/, levels/, ui/)
2. **脚本路径** — 脚本放在 `scripts/` 目录，与场景同名对应
3. **资源路径** — .tres 资源放在 `resources/` 目录
4. **素材路径** — 原始素材放在 `assets/` 目录，按类型分子目录
5. **UID 管理** — 新资源必须执行 `engine uid` 分配 UID，不要猜测
6. **导入流程** — 添加素材后必须执行 `engine import` 再使用
7. **验证习惯** — 重要变更后执行 `project validate` + `engine validate`

## 职责边界

1. **脚本逻辑** — 仅玩法程序员修改，其他角色不要改 GDScript 内部逻辑
2. **场景结构** — 仅关卡设计师调整场景树布局，其他角色不要改节点层级
3. **UI 场景** — 仅 UI 开发者创建和修改 UI 相关场景和控件
4. **素材资源** — 仅视效音效师导入和管理素材资源
5. **跨角色协作** — 需要另一角色的产出时，通过任务系统沟通，不直接修改

## 质量标准

1. 所有交付物必须附带交付摘要日志
2. 脚本类交付物需通过 `script validate`
3. 场景类交付物需通过 `scene read` 验证结构合理
4. 里程碑交付需通过 `engine validate` 无错误
5. 最终交付需通过 `export build --dry-run` 验证可构建

## 协作规范

1. 不要修改其他 Agent 正在执行的子任务
2. 遇到问题先查日志找已有方案，再尝试自己解决，最后才求助
3. 返工时必须针对审查意见逐项修复，不要遗漏
4. 实例化子场景前确认场景文件已存在
5. 每次自省笔记不要重复已有内容
